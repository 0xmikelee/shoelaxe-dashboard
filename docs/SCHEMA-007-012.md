# Frozen DDL — migrations 007–012

Reviewed and frozen at M0, before any SQL is written, so that migration `013` is not authored under
pressure halfway through the build. Files land in `../Shoelaxe/supabase/migrations/`. Every file is
wrapped in `begin; … commit;`. Forward-only — `001`–`006` are not replayable and move to
`migrations_legacy/`, with a `pg_dump --schema-only` baseline standing in for them.

Existing shape this builds on: `products`, `listings` (unique on `product_id, size, currency`),
`stock_levels`, `price_updates`, `price_history`, `media.product_images`, the `sneaker_listings` view,
`compute_listing_price`, `record_and_apply_price_update` (live at `006_stock_levels.sql:79-555`).

---

## Application timeline — read this before running anything

The file order is **not** the application order, and one operation had to move.

| Applied at | Files | Why |
|---|---|---|
| M1 | `007` | Closes a live data exposure; must not wait for the risky milestone |
| M3 | `008`, `009`, `010`, `011` | The bulk. `010` deliberately does **not** touch `stock_levels` |
| M8 | `012` | Breaking — stubs the RPC the deployed Apps Script still calls |

**The ordering problem, and the fix.** The earlier draft had `010` convert `stock_levels` from a table
into a view. That breaks the live `record_and_apply_price_update`, which inserts into it — and that RPC
stays in production until the Apps Script is cut over at M7, four milestones after `010` lands. A view
without `INSTEAD OF` triggers would fail every hourly ingest in that window. So the swap moves to
`012`, which is applied *after* cutover. `010` only creates and populates `listing_sources`.

That leaves a second, milder issue: between M3 and M7 the old RPC keeps writing `stock_levels` and
`listings.cost` while nothing writes `listing_sources`, so the new table drifts. The fix is that the
backfill lives in a **re-runnable script**, not only inside the migration:
`scripts/backfill-listing-sources.ts` is idempotent (`on conflict … do update` guarded by
`cost_at`/`last_synced_at`), is run once at M3, and is run **again immediately before cutover** at M7.
Nothing in production reads the new columns before cutover, so the drift window is harmless as long as
that second run happens. It is a step in M7's checklist, not an optional cleanup.

## 007 — worker ops and the anon revoke  · applied at M1 · low risk

```sql
create table public.worker_heartbeat (
  id int primary key check (id = 1),
  instance text not null,
  last_beat_at timestamptz not null default now());
insert into public.worker_heartbeat (id, instance, last_beat_at)
  values (1, 'none', now()) on conflict (id) do nothing;

-- ── the live exposure ────────────────────────────────────────────────────────
-- 006_stock_levels.sql:69 grants select on sneaker_listings to anon, and the view is
-- not security_invoker, so it bypasses RLS: every cost and margin is readable with the
-- public anon key. The base-table grants are harmless (RLS blocks them); the view is the hole.
drop view if exists public.sneaker_listings;
create view public.sneaker_listings with (security_invoker = true) as
  select l.id, p.product_name, p.product_sku, p.brand, l.size,
         l.cost, l.margin_percent, l.margin_fixed, l.current_price,
         sl.quantity, l.currency, l.source, l.last_source_ref,
         p.stockx_internal_id, l.created_at, l.updated_at
  from public.listings l
  join public.products p on p.id = l.product_id
  left join public.stock_levels sl
    on sl.product_id = l.product_id and sl.size = l.size;
grant select on public.sneaker_listings to authenticated, service_role;

revoke select on public.products, public.listings, public.price_updates,
                public.price_history, public.stock_levels, public.sneaker_listings from anon;
revoke select on media.product_images from anon;
revoke usage on schema media from anon;

-- Storage: 002 granted authenticated INSERT+UPDATE on storage.objects and no DELETE at all,
-- so §6.2's image delete has no policy to work through. All bucket writes go service-role
-- side instead (service_role bypasses RLS), which closes both holes at once.
drop policy if exists product_images_service_insert on storage.objects;
drop policy if exists product_images_service_update on storage.objects;
-- product_images_public_read stays: the bucket is public by design.

alter table public.worker_heartbeat enable row level security;
create policy worker_heartbeat_select_authenticated on public.worker_heartbeat
  for select to authenticated using (true);
grant select on public.worker_heartbeat to authenticated, service_role;
```

**Column-order warning.** Recreating `sneaker_listings` preserves the 006 column order exactly,
including `quantity` sitting before `currency` — anything doing positional `select *` unpacking must
keep working. Do not "tidy" the order.

## 008 — enums, constraint hygiene, CHECK widening · applied at M3 · low risk

### Enums

Six, and the reason is not tidiness: `supabase gen types` renders enums as TypeScript string-literal
unions, which is what makes the `decide()` switch exhaustiveness-checked at compile time.

```sql
create type public.listing_source_slot     as enum ('stockx','in_house');
create type public.listing_approval_status as enum
  ('approved','pending_new','pending_price','needs_margins','rejected','inactive');
create type public.margin_source           as enum ('override','group','default');
create type public.price_update_status     as enum ('pending','applied','skipped','rejected','error');
create type public.price_history_change_type as enum
  ('cost','margin_percent','margin_fixed','listing_price','quantity',
   'listing_status','margin_source','manual_price');
create type public.job_status              as enum
  ('queued','running','succeeded','failed','cancelled','deferred');

alter table public.price_updates drop constraint price_updates_status_check;
alter table public.price_updates
  alter column status type public.price_update_status using status::public.price_update_status;
```

**Not converted, deliberately:** `price_updates.outcome` (14 values, append-only log data, and
`alter type … add value` cannot run in the same transaction as a statement using the new value);
`currency` (the schema stays per-currency on purpose); `price_updates.source` / `price_history.source`
(the wire vocabulary gains `'dashboard'` — a widened CHECK avoids coupling the protocol to a DB type).

### Constraint names that lie

Renaming these here means `010`/`011` can reference sane names.

-- price_updates.price was renamed to cost in 005; the CHECK kept the old auto-name

## 009 — groups, settings, users, ops tables · applied at M3 · medium risk

### product_groups, and the ordering that matters

```sql
create table public.product_groups (
  id uuid primary key default gen_random_uuid(),
  name text not null unique,
  margin_percent numeric(8,4) check (margin_percent is null or margin_percent >= 0),
  margin_fixed   numeric(12,2) check (margin_fixed   is null or margin_fixed   >= 0),
  is_default boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now());
create trigger product_groups_set_updated_at before update on public.product_groups
  for each row execute function public.set_updated_at();
create unique index product_groups_single_default_idx
  on public.product_groups (is_default) where is_default;

-- Margins are NULL on purpose: every product belongs to some group, so a rule on the default
-- group would make the Screen 2 system default unreachable dead config.
insert into public.product_groups (name, margin_percent, margin_fixed, is_default)
  values ('預設分組', null, null, true);

create function public.protect_default_group() returns trigger language plpgsql as $$
begin
  if (tg_op = 'DELETE' and old.is_default)
     or (tg_op = 'UPDATE' and old.is_default and not new.is_default) then
    raise exception 'the default product group cannot be deleted or demoted';
  end if;
  return coalesce(new, old);
end $$;
create trigger product_groups_protect_default
  before delete or update of is_default on public.product_groups
  for each row execute function public.protect_default_group();
```

Then, in exactly this order — adding the column already NOT NULL rewrites the table and baking in a
default would freeze a group id into the catalogue; setting NOT NULL before the backfill just fails:

```sql
alter table public.products add column product_group_id uuid
  references public.product_groups(id) on delete restrict;      -- nullable, no default
update public.products
  set product_group_id = (select id from public.product_groups where is_default);
alter table public.products alter column product_group_id set not null;
create index products_group_idx on public.products (product_group_id);
```

`on delete restrict`, not cascade: deleting a group must go through the app path that reassigns its
products to the default group and re-runs the pricing decision for each affected listing.

## 010 — listing_sources · applied at M3 · **highest risk**

```sql
create table public.listing_sources (
  id uuid primary key default gen_random_uuid(),
  listing_id uuid not null references public.listings(id) on delete cascade,
  source public.listing_source_slot not null,
  cost numeric(12,2) check (cost is null or cost >= 0),
  cost_at timestamptz,                   -- see note
  quantity integer not null default 0 check (quantity >= 0),
  last_source_ref text, last_synced_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint listing_sources_listing_source_unique unique (listing_id, source));
create trigger listing_sources_set_updated_at before update on public.listing_sources
  for each row execute function public.set_updated_at();
```

**Why `cost_at` exists and the brief's DDL is not enough.** `base_cost` is defined as the cost from the
most recently applied update from either source, which is a denormalisation of "whichever source row
was most recently written *with a non-null cost*". `last_synced_at` also moves on quantity-only syncs,
so using it would let a StockX quantity ping steal base-cost ownership from a fresher in-house cost.

**Two vocabularies, mapped in exactly one place** (`lib/domain/sources.ts`): the *event* vocabulary on
`price_updates.source` / `price_history.source` is `stockx | google_sheet | dashboard` (what the wire
carries); the *slot* vocabulary on `listing_sources.source` is `stockx | in_house` (what is stored).

### Pre-flight, before the backfill

```sql
select count(*) from (
  select product_id, size from public.listings group by 1,2 having count(*) > 1) t;
```
Must be **0**. `listings` is unique on `(product_id, size, currency)` but `stock_levels` on
`(product_id, size)`, so a product+size with two currency listings would fan one quantity out to both
and the totals would not reconcile. In an HKD-only catalogue this is zero; if it is not, decide which
listing owns the stock before running anything.

### Pass 1 — each listing's own declared source

```sql
insert into public.listing_sources (listing_id, source, cost, cost_at, quantity,
                                    last_source_ref, last_synced_at)
select l.id,
       (case when l.source = 'stockx' then 'stockx' else 'in_house' end)::public.listing_source_slot,
       l.cost,
       case when l.cost is not null then l.updated_at end,
       case when l.source = 'stockx' then 1 else coalesce(sl.quantity, 0) end,
       l.last_source_ref, l.updated_at
from public.listings l
left join public.stock_levels sl on sl.product_id = l.product_id and sl.size = l.size
on conflict (listing_id, source) do nothing;
```

### Pass 2 — the one that gets skipped

`stock_levels` is keyed on `(product_id, size)` and is source-agnostic, so a listing whose
`source = 'stockx'` can still hold real in-house stock. Skipping this loses that inventory — and
because Shopify inventory is in-house-only, **every affected variant would publish at 0 stock**,
silently, and nobody would find out until publishing is enabled.

```sql
insert into public.listing_sources (listing_id, source, cost, quantity, last_synced_at)
select l.id, 'in_house'::public.listing_source_slot, null, sl.quantity, sl.updated_at
from public.listings l
join public.stock_levels sl on sl.product_id = l.product_id and sl.size = l.size
where l.source = 'stockx' and sl.quantity > 0
on conflict (listing_id, source) do nothing;
```

### Invariants — assert as counts, not spot checks

```sql
-- every listing has at least one source row
select count(*) from public.listings l
  where not exists (select 1 from public.listing_sources s where s.listing_id = l.id);   -- 0

-- in-house quantity reconciles with the old table, per (product, size)
select count(*) from (
  select l.product_id, l.size,
         max(sl.quantity) as old_qty,
         max(case when s.source = 'in_house' then s.quantity else 0 end) as new_qty
  from public.listings l
  join public.stock_levels sl on sl.product_id = l.product_id and sl.size = l.size
  left join public.listing_sources s on s.listing_id = l.id
  group by 1,2) t where old_qty is distinct from new_qty;                                 -- 0
```

`stock_levels` is **not** touched here — see the timeline note at the top.

## Deviations from the brief's §4, and why

| Deviation | Reason |
|---|---|
| `jobs` / `job_items` instead of `group_apply_jobs` / `group_apply_job_items` | The table also carries the settings fan-out and the `margin_source` recompute — same shape, three triggers. `failed jsonb` also cannot express "not yet done" or be claimed atomically |
| `listing_sources.cost_at` | `last_synced_at` moves on quantity-only syncs and would corrupt base-cost selection |
| `crawl_runs.run_id text unique` | A run spans several chunk requests and the brief's DDL gives it no natural key |
| `shopify_sync_jobs_pending_unique` | Bounds the deferred backlog at one row per listing |
| `price_updates.engine` | Five legacy outcome values are re-emitted with new meanings; `/approvals` reads both eras |
| `allowed_users.email text` not `citext` | Extension placement and opaque generated types |
| `stock_levels` swap moved from `010` to `012` | It would break the live RPC four milestones before cutover |

## One caveat about every constraint name in this document

Only seven constraints in `001`–`006` were explicitly named (`product_images_has_location`,
`products_sku_unique`, `listings_product_size_currency_unique`, `stock_levels_product_size_unique`,
`price_updates_outcome_check`, and the two dropped in `004`). Every other name used above —
`price_updates_status_check`, `price_history_quantity_check`, `price_history_previous_quantity_check`,
`price_history_source_check`, `price_updates_source_check` — is **inferred** from PostgreSQL's
auto-naming rule for inline `check` clauses. The inference is sound (each was verified against the
statement that created it, e.g. `003_listing_quantity.sql:7-13`), but auto-naming can append a numeric
suffix on collision.

So the migrations use `drop constraint if exists` throughout, and `008` opens with a verification query
that fails loudly rather than silently skipping a rename:

```sql
select conrelid::regclass as tbl, conname
from pg_constraint
where conrelid in ('public.listings'::regclass, 'public.price_updates'::regclass,
                   'public.price_history'::regclass)
  and contype = 'c'
order by 1, 2;
```

Run it against the restored production copy during the M3 rehearsal and reconcile it with this document
before applying anything to production. A silently-skipped `drop constraint if exists` leaves a
`quantity > 0` CHECK in place, and sold-out stock then fails at runtime rather than at migration time.
